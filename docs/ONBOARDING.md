# V2CC Mac mini 机主接入与交付操作手册

从一台新 Mac mini 到手，到交付给客户使用的完整操作顺序。每一步写明执行账户、命令、
预期结果、异常处理和验证状态。脚本的名称、参数、提示和输出都取自本仓库当前的
脚本；脚本细节以 [README.md](../README.md) 和 [docs/test-plan.md](test-plan.md) 为准。

## 角色和账户

| 名称 | 含义 |
| --- | --- |
| 机主 | 这台 Mac mini 的所有者，机器放在机主处 |
| 平台、运营方 | V2CC 平台一方，在自己的电脑上生成入口命令，指导、维护和验收 |
| 客户 | 最终通过远程桌面使用客户账户的人 |
| `<机主管理员>` | 机主自己的本机管理员账户。占位符，手册和仓库里不写真实账户名 |
| `v2ccops` | 平台维护管理员（运维）的本机管理员账户，部署、自动登录、回退和需要管理员权限的维护都在这里做。账户名是默认值，脚本用 `--ops <账户名>` 可以改，待机主确认（「五个设置问题的默认做法」第 1 项） |
| `v2cc` | 客户的普通账户（标准用户），没有管理员权限。自动登录进入它，UU远程 在它的会话里运行 |
| 测试机 A、测试机 B | 两台实测过的 Mac mini（上一版做法）。手册里只用这两个代号 |

每一步在哪个账户里做：

| 步骤 | 执行账户 | 需要管理员权限 |
| --- | --- | --- |
| 生成入口命令（`tools/make-entry-command.sh`） | 运营方自己的电脑 | 否 |
| 新建 `v2ccops` 和 `v2cc` | 机主，在 `<机主管理员>` 里 | 是 |
| 安装 UU远程 | `v2ccops`（或机主在 `<机主管理员>` 里） | 是 |
| 登录和设置 UU远程 | `v2cc` 的桌面，由现场的人操作 | 授予系统权限时可能要（尚未验证） |
| 系统部分：入口命令、`bootstrap.sh`（含部署） | `v2ccops` | 是 |
| 7×24 在线设置 | 部署时由系统配置写入，整机生效；即 `v2ccops` 运行部署时 | 是 |
| 客户账户部分：入口命令、`customer-setup.sh` | `v2cc` | 否 |
| FileVault 风险告知 | 运营方告知，机主确认 | 否 |
| 关闭 FileVault | 机主本人，在 `<机主管理员>` 里 | 是 |
| `./auto-login.sh enable`、`disable` | `v2ccops`。自动登录的对象永远是系统配置登记的客户账户 `v2cc` | 是 |
| `./auto-login.sh status`、`./verify.sh` | 任何账户。`verify.sh` 里客户账户的那部分检查只在 `v2cc` 里做 | 否 |
| `./rollback.sh`（`--list` 除外） | `v2ccops`（上次部署的记录在这个账户里） | 是 |
| 重启后自动登录进入 | `v2cc` | |
| 远程会话到达 | `v2cc` 的桌面：UU远程 运行在自动登录的 `v2cc` 会话里 | |
| 客户申请的、需要管理员权限的安装 | 运维用 `v2ccops`：授权对话框按「五个设置问题的默认做法」第 2 项在远程会话里输入；要用 `sudo` 的在 `v2ccops` 自己的会话里 | 是 |
| 清理凭据 | `v2cc` 和 `v2ccops` 各自运行 | 否 |

通用规则：

- 遇到"异常处理"里写的停止条件就停下，保留终端的全部输出，交给运营方，不要手工绕过。
- 脚本都不用 `sudo` 启动。需要管理员授权时脚本会说明原因，再由 macOS 询问当前账户的
  登录密码。在 `v2cc` 里运行需要管理员权限的脚本时，脚本会在做任何事之前停下。
- 管理员账户的密码只在两种地方输入：机器旁、在该管理员账户自己的会话里；或者按
  「五个设置问题的默认做法」第 2 项，由运维通过远程会话只输入到 macOS 自己弹出的
  授权对话框里。不要输入到 `v2cc` 会话里的「终端」或任何应用里：`v2cc` 会话里运行
  什么软件由客户决定。
- 不写绝对承诺。本手册只记录观察到的结果。这些设置不保证机器永不重启，也不保证停电后
  一定能远程连接（见 README「7×24 在线设置」）。
- 密码、令牌、入口命令、UU远程 的设备代码、序列号、IP 地址、主机名、真实账户名、
  人名、电话和地址，都不写进本仓库、GitHub 的 issue 或 PR、截图和聊天记录的存档里。

## 客户普通账户：能做什么、要平台做什么

客户规则（DEC-0007 §93）：客户使用专用的普通账户，没有管理员权限；常用开发工具
预装；`brew install` 不需要密码；Homebrew、npm、pip 的安装都在客户自己的账户下；
需要管理员权限的安装由平台按申请完成；平台和机主保留管理员权限；客户不得删除或
卸载平台安装的组件。

在 `v2cc` 里不需要管理员密码的（桩测试覆盖了设置和检查，真机上【尚未验证】，见 6.4）：

| 操作 | 怎样做到 |
| --- | --- |
| 使用预装的 `git`、`node`、`npm`、`python3`、`uv`、`claude`，以及 Xcode Command Line Tools 带的 `clang`、`make` | 系统配置和 Xcode Command Line Tools 提供；Claude Code 装在 `~/.local/bin` |
| `brew install`、`brew upgrade`、`brew uninstall` 软件包 | 部署把 `/opt/homebrew` 交给 `v2cc`（属主 `v2cc`，组 `staff`，其他账户不可写），和 Homebrew 官方安装脚本给普通账户的结果相同 |
| `brew install --cask` 能装进 `~/Applications` 的应用 | `~/.zprofile` 里的 `HOMEBREW_CASK_OPTS="--appdir=$HOME/Applications"` |
| `npm install -g` | 预装的 `node` 在只读的 Nix 目录里，谁都不能往那里装；`~/.npmrc` 把位置改为 `~/.npm-global`，`~/.zprofile` 把 `~/.npm-global/bin` 加进 PATH |
| Python：`uv`（`uv venv`、`uv pip install`、`uv tool install`）、`python3 -m venv` | 系统配置预装 `python3` 和 `uv`。预装的 `python3` 没有全局的 `pip`，软件包装进虚拟环境（在客户自己的目录里）或交给 `uv`；`uv tool install` 的命令装进 `~/.local/bin`。终端里的 `pip3` 是 Xcode Command Line Tools 带的另一个旧版 Python 的，不要用它 |
| Claude Code 自己升级 | 装在客户自己的主目录（普通账户下的自动升级尚未在真机验证，V23） |
| Docker Desktop（装好之后） | 由运维按 6.5 用 `--user=v2cc` 安装；Docker 的文档说装好之后运行不需要管理员（尚未在真机验证，V21） |

客户规则里本修改稿还做不到、或只做到一部分的：

| 规则 | 现状 |
| --- | --- |
| `brew install` 不需要密码 | 只对软件包和能装进 `~/Applications` 的 cask 成立。安装程序是 `.pkg` 的 cask、要写 `/Applications` 或 `/Library` 的 cask、安装过程中要求 `sudo` 的少数软件包，仍然要管理员，只能由平台代装。机主已经在用 `/opt/homebrew` 的机器上，机主不同意交给客户时，客户完全不能 `brew install`（第 15 节 M5） |
| Homebrew 装在客户自己的账户下 | 归客户所有，但位置是 `/opt/homebrew`，不在客户的主目录里。Homebrew 只为这个位置提供预编译包，换到主目录里会大量改为从源码编译 |
| 常用开发工具预装 | 预装的是上表第一行这些，以及按 6.5 由运维手工安装的 Docker Desktop。"常用"没有更具体的清单，其他工具由客户自己 `brew install`。Docker Desktop 没有写进脚本：它的下载地址不带版本、没有可以固定的校验值，`--accept-license` 会替人接受 Docker 的订阅协议（较大企业的商业使用要付费），而且 `--user` 只允许一个账户使用 |
| 需要管理员权限的安装由平台按申请完成 | 弹出 macOS 授权对话框的操作（系统设置里的权限、`/Applications` 里的应用、`.pkg` 安装程序），运维按默认做法第 2 项在远程会话里输入 `v2ccops` 的名字和密码；要在「终端」里用 `sudo` 的，要进入 `v2ccops` 自己的会话，从远程切换过去是否可行尚未验证（V18），不可行时要有人在机器旁登录。运维直接 `brew install` 会失败（`/opt/homebrew` 只有客户能写），替客户装软件包用 `sudo -u v2cc -H /opt/homebrew/bin/brew install <包>`（尚未验证，V22） |
| 客户不得删除或卸载平台安装的组件 | 归 root 所有、或放在只有管理员能写的位置的部分（Nix、nix-darwin 系统配置、Xcode Command Line Tools、`/Applications` 里的应用、UU远程 的系统服务、锁屏登录项）普通账户删不掉（`/Applications` 这一项见 test-plan D 节 D7，尚未验证）。但 Homebrew 和其中的软件包（为了 `brew install` 不需要密码，它们归客户所有）、Claude Code、`~/.zprofile` 和 `~/.npmrc` 里的设置、UU远程 在客户会话里的登录和开关，客户都能删除或关掉。这一条对它们只能是使用规则，脚本拦不住；`./verify.sh` 能发现其中一部分 |
| 平台和机主保留管理员权限 | 做到。机主管理员不变，平台有自己的管理员账户。平台维护管理员账户的密码由谁保管，见待定决定 |

## 7. 7×24 在线设置（电源和休眠）

这些设置不需要单独的命令：它们是系统配置的一部分，在 5.4 的 `[5/7]` 激活时由
`v2ccops` 运行的部署写入。它们是 macOS 的整机设置，对本机所有账户生效，
包括机主账户。

| 设置 | 值 | 方式 |
| --- | --- | --- |
| 系统空闲时自动睡眠 | 关闭（显示器仍按原设置自动关闭） | `pmset -a sleep 0` |
| 断电后恢复供电时自动开机 | 开启（本机没有这项设置时跳过） | `pmset -a autorestart 1` |
| 唤醒以供网络访问 | 开启（本机没有这项设置时跳过） | `pmset -a womp 1` |
| 闲置后自动退出登录 | 关闭 | `AutoLogOutDelay = 0` |
| 自动安装 macOS 更新 | 关闭 | `AutomaticallyInstallMacOSUpdates = false` |

- 改动之前，激活脚本先把原值记到 `/var/db/v2cc/always-on-before.txt`，只记一次。
  本机支持的电源设置里只要有一项原值读不出来，就在这里停止，一项都不改。
- 设置只在部署激活时写入，不在每次开机时重写。之后有人在系统设置里改了某一项，
  脚本不会改回去，`./verify.sh` 会报告出来。`v2cc` 是普通账户，改不了这些整机设置。
- 关闭自动安装更新之后，安全修复不会自己装上，必须有人在维护时段里手工安装。谁装、
  什么时候装尚未决定（见待定决定）。脚本能确认的只是这个开关已经关闭；它在
  macOS 27 上能否挡住更新自动安装和重启，尚未在真机验证（test-plan C 节阶段 4 的
  4.2）。检查更新、更新通知、安全数据和后台安全更新的自动安装都没有动。

**7.1 确认设置已经生效**

## 8. 关闭 FileVault：风险告知与确认

FileVault 开启时，机器重启后停在磁盘解锁界面，要有人在机器旁输入密码；在此之前任何
远程软件都连不上，也无法自动登录。要让机器重启后自己回到 `v2cc` 的桌面，必须先关闭
FileVault。它是整块磁盘的一个开关，关闭后本机所有账户（包括机主账户）的磁盘保护都
降低。脚本不会关闭 FileVault，运营方也不替机主关闭。

**8.1 查看当前状态**

- 执行账户：任何账户
- 命令：

  ```sh
  cd ~/v2cc-mac-setup
  ./auto-login.sh status
  ```

- 预期结果：只读，显示系统配置登记的客户账户（`v2cc`）、FileVault 的状态、系统设置
  的自动登录账户、保存的登录凭据 `/etc/kcpassword` 是否存在、是否由本脚本设置、
  登录后立即锁屏是否安装
- 异常处理："系统配置登记的客户账户：无"：部署的是更早的版本，先完成第 5 节（已经
  交付的机器按第 15 节）
- 状态：【仅自动化测试或演练验证】（上一版在运营方的 Mac 上只读运行过）

**8.2 向机主说明风险并取得确认**

- 执行账户：运营方说明，机主确认
- 命令：无。把第 11 节的告知文字完整给机主看，机主在确认行上确认
- 预期结果：机主明确同意，确认记录保存在仓库之外。没有这份确认就不做 8.3 和第 9 节
- 异常处理：机主不同意时到此为止。这台机器保持 FileVault 开启，每次重启都需要有人
  在机器旁输入密码，不能作为重启后可以自己恢复远程连接的机器交付
- 状态：【尚未验证】告知文字没有定稿，测试机上是否做过告知和确认没有记录（已知限制 F5）

- 异常处理：几小时内没有完成解密时停止，交给运营方
- 状态：【尚未验证】R3（上一版做法）报告重启后自动登录，而 FileVault 开启时 macOS
  不允许自动登录，由此推断那台机器当时 FileVault 是关闭的；但由谁、何时、怎样关闭

## 9. 自动登录

前提：第 5、7 节通过（7×24 在线设置已生效），第 8 节完成。自动登录只为系统配置登记
的客户账户 `v2cc` 开启，而且只在它是普通账户时开启；一台机器只能有一个自动登录账户。
命令在 `v2ccops` 里运行；`sysadminctl` 询问的是 `v2cc` 的密码。

**9.1 先演练，查看开启条件**

- 执行账户：`v2ccops`
- 命令：

  ```sh
  cd ~/v2cc-mac-setup

  ```

- 预期结果："检查开启条件（只读）..."下面三项 ✓："目标账户 v2cc 是系统配置登记的
  客户账户，是普通账户，不是运行本脚本的账户"、FileVault 已关闭、7×24 在线设置已
  生效。随后列出要确认的后果，再显示"[演练] 将执行：sudo sysadminctl -autologin set
  -userName v2cc -password -"和"演练结束，系统没有任何改动。"
- 异常处理（脚本直接停止，什么都不改）：
  - "开启或关闭自动登录需要管理员权限"：换到 `v2ccops` 里运行
  - "本机还没有部署 V2CC 系统配置。"：先完成第 5 节
  - "本机的系统配置没有登记客户账户"：部署的是更早的版本，按第 15 节
  - "客户账户 v2cc 是管理员。自动登录只用于普通账户"：回到 4.2，或按第 15 节
  - "FileVault 没有关闭（...）。"：回到第 8 节
  - "7×24 在线设置没有生效"：回到第 7 节，让 `./verify.sh` 通过
  - "本机已经为账户「...」开启了自动登录。"：已有别的账户自动登录，脚本不会替换它，
    交给运营方
- 状态：【仅自动化测试或演练验证】

**9.2 开启自动登录**

- 执行账户：`v2ccops`，由人在机器旁的「终端」里操作
- 命令：

  ```sh
  ./auto-login.sh enable
  ```

- 过程：脚本先做 9.1 的检查并列出后果，然后要求输入账户名 `v2cc` 确认（输入其他
  任何内容都会取消，`V2CC_ASSUME_YES` 跳不过这一步，不是交互终端也会被拒绝）；
  接着 macOS 询问 `v2ccops` 的登录密码做管理员授权；最后由 macOS 自带的
  `sysadminctl` 在终端里询问 `v2cc` 的登录密码并保存
- 密码：只在这两处提示下由人输入。不写进命令参数、环境变量、脚本、仓库、聊天记录
  和命令历史。脚本自己接触不到密码
- 预期结果："自动登录账户：v2cc"；"登录凭据由系统保存在 /etc/kcpassword
  （root:600）"；"自动登录已开启：下次开机起，本机会直接进入账户 v2cc。"
- 异常处理：
  - "系统工具没有完成自动登录的设置。"或"读回检查未通过"：脚本会自动撤销，以它
    最后一行的说明为准（此前的自动登录是原样保留，还是已经关闭）。保留输出交给
    运营方
  - "撤销没有成功"：运行 `./auto-login.sh status` 查看，再运行
    `./auto-login.sh disable`，保留输出交给运营方
- `--lock-after-login`（`v2cc` 每次登录后立即关闭显示器并锁屏）是待定项，默认不带。
  登录项装在 `/Library/LaunchAgents/com.v2cc.lock-after-login.plist`，归 root 所有，只在
  `v2cc` 的会话里起作用。它在 macOS 27 上能否生效、锁屏后 UU远程 能否输入密码解锁
  都尚未验证（test-plan C 节阶段 2 的 2.7）
- 状态：【仅自动化测试或演练验证】上一版做法：重启后 `v2cc` 自动登录在 R3 的口头
  报告里通过，当时 `v2cc` 是管理员，是否用这个脚本开启没有记录（已知限制 F6）。
  `sysadminctl` 在 macOS 27 上是否自己在终端询问密码并完成设置、`/etc/kcpassword`
  的属主和权限是否为 root:600，都尚未在真机验证

下面是 8.2 使用的告知文字，是现阶段的版本，措辞没有定稿。使用时完整给机主看，不要

> **关闭 FileVault 和开启自动登录之前，请确认你清楚这些后果**

> 1. FileVault 是 Mac 的磁盘加密开关，一台机器只有一个，对机器上所有账户同时生效，

> 2. FileVault 开启时，机器每次重启都停在磁盘解锁界面，必须有人在机器旁输入密码。

>    客户账户 `v2cc` 的桌面。

>    这层保护。
> 4. 开启自动登录之后，这台机器每次开机都直接进入 `v2cc` 的桌面。任何能接触到
>    这台机器的人（家人、访客、维修人员、窃贼）打开它，就能使用这个账户：里面的

>    打开你的账户和平台的管理员账户。
> 5. `v2cc` 的登录密码会以可以还原的形式保存在这台机器的磁盘上。它只是混淆，不是
>    加密，能在这台机器上取得 root 权限的人可以读出它。

>    脚本和运营方都不会替你关闭。

>    密钥。重新开启之后，每次重启又需要有人在机器旁输入密码。

## 12. 回退

所有回退命令都在 `v2ccops` 的 `~/v2cc-mac-setup` 目录下运行：上次部署的
记录保存在这个账户的 `~/.local/state/v2cc/last-deploy` 里，而且回退需要管理员权限。
在 `v2cc` 里运行时脚本会直接停下。回退不删除任何账户主目录里的文件。回退会改动
整机的系统配置，和部署一样需要先获得批准。

| 目的 | 命令 | 实际行为 |
| --- | --- | --- |
| 查看系统配置的历史版本 | `./rollback.sh --list` | 只读，任何账户都能运行，列出历史版本的链接和各自指向的系统配置 |
| 回到上次部署之前的系统配置 | `./rollback.sh` | 显示"回退目标"和"该配置管理的账户"，问一次 `[y/N]`，要求管理员授权，重新激活那个配置，显示"已回退到：..." |
| 回到指定的系统配置 | `./rollback.sh --to <系统配置路径>` | 同上，目标取自参数。不能和 `--settings` 一起使用 |
| 只把 7×24 在线设置恢复为启用前的原值 | `./rollback.sh --settings` | 问一次 `[y/N]`，按 `/var/db/v2cc/always-on-before.txt` 逐项恢复并读回检查，原来没有的设置会被删除，然后把记录改名为 `always-on-before.txt.restored` |
| 关闭自动登录 | `./auto-login.sh disable` | 问一次 `[y/N]`，关闭自动登录，删除 `/etc/kcpassword`、登录后立即锁屏的登录项（包括旧版本放在 `v2cc` 目录里的那份）和标记 |
| 只看将要做什么 | 在上面的 `./rollback.sh` 命令前加 `V2CC_DRY_RUN=1`；`./auto-login.sh disable --dry-run` | 只显示"[演练]"行，不改动。`rollback.sh` 不接受 `--dry-run` 参数，只认环境变量 |

要点：

- 7×24 在线设置保存在 macOS 里，不在 Nix 里，重新激活旧的系统配置并不会撤销它们。
  所以只有回退目标不包含这些设置时，`./rollback.sh` 才会接着恢复它们，并显示"该
  配置不包含 7×24 在线设置：电源、自动退出登录和系统更新设置也会恢复为启用前的
  值。"。在两个都包含这些设置的配置之间回退，设置保持开启。
- 这次部署就是本机的首次部署时，`./rollback.sh` 报"上次部署是本机的首次部署，没有
  可回退的系统配置。"，这时用 `./rollback.sh --settings`。当前系统配置仍然包含这些
  设置，所以在重跑 `./bootstrap.sh` 之前 `./verify.sh` 会报告不一致，重跑之后这些
  设置会再次启用。
- 有设置恢复不了时，记录保留在 `/var/db/v2cc/always-on-before.txt`，处理后运行
  `./rollback.sh --settings` 重试。没有这份记录时脚本报"无法恢复"，设置不能自动
  恢复。
- 其他报错："没有找到上次部署的记录"：在运行部署的那个账户里运行；或者用 `--list`
  查看，再用 `--to` 指定。"系统配置不存在或已被清理"：目标已不在本机，交给运营方。
  "当前系统已经是该配置，无需回退。"：不需要处理。
- Homebrew 交给 `v2cc` 这一步不随系统配置回退。
- 自动登录不随系统配置回退，要单独运行 `./auto-login.sh disable`。它结束时提示两件
  要人工完成的事：修改 `v2cc` 的登录密码（它曾以可还原的形式保存在磁盘上）；由
  机主重新开启 FileVault 并保存新的恢复密钥。
- 通过远程会话关闭自动登录或恢复电源设置之前要想清楚：之后的下一次重启会停在登录
  窗口，断电后也可能不再自己开机，需要有人到机器旁。
- 部署时激活失败的自动回退由脚本自己完成（见 5.4），不需要人运行这些命令。

状态：【仅自动化测试或演练验证】这一节的全部命令都只在桩测试里验证过，没有真机
演练记录（已知限制 F13、V14；test-plan 的 B6、C 节阶段 1 的 1.9 和阶段 2 的 2.12）。

### 参考：怎样把口头报告变成有记录的证据

下面只留作参考，不是测试计划，没有人运行过。以后要做时仍要按规则获得批准；重启会
中断正在进行的工作。

1. 记下重启前的时间。在那台测试机上重启，之后没有人接触机器。
2. 从第二台设备用 UU远程 连接，记下从重启到设备显示在线的用时。
3. 连上之后，在远程会话里 `v2cc` 的「终端」运行下面的命令，把全部输出保存成文本：

   ```sh
   sysctl -n kern.boottime
   fdesetup status
   id -Gn
   cd ~/v2cc-mac-setup
   ./auto-login.sh status
   ./verify.sh
   ```

4. 再重复两次，一共三次。

这些输出能说明什么：

| 输出 | 说明 |
| --- | --- |
| `sysctl -n kern.boottime` | 开机时间就是这次重启的时间，证明机器确实重启过 |
| `fdesetup status` 显示 `FileVault is Off.` | 重启后不会停在磁盘解锁界面 |
| `id -Gn` 里没有 `admin` | 远程会话里的 `v2cc` 是普通账户 |
| `./auto-login.sh status` | 系统设置的自动登录账户是不是 `v2cc`，登录凭据文件是否存在，是否由脚本设置 |
| `./verify.sh` 里"重启后自动登录账户 v2cc（由 auto-login.sh 于 ... 设置）" | 自动登录是通过脚本开启的。如果显示的是"不是通过 ./auto-login.sh 设置的"，说明是在系统设置里直接开启的（对应已知限制 F6） |
| `./verify.sh` 里"UU远程 系统服务：已加载。"和"UU远程 在当前登录会话中：已加载。" | UU远程 在这次登录会话里已经运行 |
| `./verify.sh` 结尾"验证通过。" | 部署、Homebrew 归属、客户账户的使用环境和 7×24 在线设置在这台机器上是完好的 |
| 这些命令是在远程会话里输入的，加上第二台设备上的一张截图 | 远程连接成功，键盘可用 |

注意：

- 脚本的输出说明的是设置和服务的状态。"重启后没有人碰过机器"这一点脚本证明不了，
  要靠现场的人确认，或者机器旁确实没有人。
- 输出和截图里会有账户名、系统路径，截图里可能有设备代码。只保存在仓库之外，不贴进
  GitHub。
- 有了三次完整输出之后，第 17 到 21 项才能在那一台机器上改标为【已在真机验证】。
  另一台测试机和以后的每台机器仍然要各自做一遍。
